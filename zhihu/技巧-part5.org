  - 一句话概括：一篇面向 2018 年之后 Vim 8 的 C/C++ 开发环境搭建指南，按插件管理、符号索引、自动索引、编译运行、动态检查、代码补全、函数列表、文件切换、参数提示逐环节推荐现代插件与配置。
  【方法/论点要点】
  - 插件管理：别再用 Vundle，改用 vim-plug——全异步安装（50 个插件一分钟内）、更新快、支持延迟加载（~on~ / ~for~）、可指定分支或 tag、单文件便于纳入 dotfiles，且用 ~:PlugUpgrade~ 自我更新；建议给插件分组，vimrc 里只选启用哪些组。
  - 符号索引：不要排斥 ctags（支持 50+ 种语言，Vim 集成最好、依赖最少）。配置要写对：~set tags=./.tags;,.tags~——tag 文件名前面加点避免污染项目，分号表示找不到就向上递归到父目录，逗号后表示同时在 Vim 当前目录查找。并升级到 Universal Ctags（Exuberant Ctags 已停止维护近十年），注意用 ~--output-format=e-ctags~ 保持兼容。
  - 自动索引：用 vim-gutentags，做两件事——靠 ~.git/.svn/.project~ 等标志向上递归确定工程目录；增量更新对应工程的 ~.tags~ 并保持符号排序以便二分查找。配置要点：~gutentags_project_root~、~gutentags_ctags_tagfile~、把 tags 放入 ~/.cache/tags~ 避免污染工程、~gutentags_ctags_extra_args~ 加 ~--fields=+niazS~ 等。建议多用 ~CTRL-W ]~ 新窗口跳转、~CTRL-W }~ 预览，少用 ~CTRL-]~。
  - 编译运行：用 AsyncRun 后台运行 shell 命令并把结果输出到 quickfix。单文件 ~F9~ 编译、~F5~ 运行（~-cwd=$(VIM_FILEDIR)~、~-raw~）；项目用 ~<root>~ 或 ~$(VIM_ROOT)~ 表示工程路径，配置 ~g:asyncrun_rootmarks~，~F7~ make、~F8~ make run、~F6~ make test、~F4~ cmake。快捷键总览：F4 生成 Makefile、F5 单文件运行、F6 项目测试、F7 项目编译、F8 项目运行、F9 单文件编译、F10 开关 quickfix。注意 C 标准库后台运行会缓存标准输出，需 ~fflush(stdout)~ 或 ~setbuf(stdout, NULL)~；C++ 用 ~std::endl~ 即可。Windows GVim 可用 ~-mode=4~ 弹新 cmd 窗口。
  - 动态检查：别用老的 syntastic（不能实时、保存即卡），改用实时 linting 的 ALE（支持 gcc/clang/cppcheck/clang-format 等，保存前就实时标注错误、侧栏提示、红色波浪线）。
  - 代码补全：传统 omni 补全语义弱、无法后台运行；新一代 YCM/Deoplete 支持异步与基于 clang 的语义补全，C/C++ 推荐 YCM（Deoplete 的 clang 补全不稳定、吃内存）。配置要点：输入两个字符即触发语义补全（~ycm_semantic_triggers~）、关闭预览窗口与诊断 UI（~ycm_show_diagnostics_ui=0~）保持清静，诊断交给 ALE。
  - 函数列表：别再同步等待 ctags 的 tagbar（保存变卡），改用 LeaderF 的 ~:LeaderfFunction!~ 全异步显示函数列表，绑定 ~ALT+P~，可模糊匹配搜索、TAB 切换列表筛选，不占屏幕空间。
  - 文件切换：用 LeaderF 代替 CtrlP，支持文件、MRU、Buffer 名称搜索，~CTRL+P~ 文件搜索、~CTRL+N~ MRU、~ALT+N~ Buffer，匹配效率高于 CtrlP/Fzf；浏览新项目可用 NERDTree 或更 Vim 式的 vim-dirvish（按 ~-~ 在当前窗口回到所在目录）。头文件/源文件切换用 a.vim 或自己两行脚本。
  - 参数提示：用 echodoc 无缝搭配 YCM，靠 libclang 在命令行显示参数并高亮当前参数位置；配合 ~set noshowmode~ 把底部模式提示让给 echodoc。
  - 结尾参考：《Vim 8 中的 C/C++ 编译运行》《Vim 中文版入门到精通》《Vim 中文速查表》，并给出 vimzh 交流群。

  - 一句话概括：不用堆插件，而是围绕自己的真实工作流「发现问题→找更快的方式→习惯化」不断循环，用 VimScript 逐个打磨痛点，并给出透明窗口、跨窗口滚动、Tag 预览、函数原型、异步编译等八个具体例子。
  【方法/论点要点】
  - 核心心法（据 Bram 的视频）：1 检测工作流里哪里浪费时间；2 寻找更快的方式（官方文档、他人经验、自己写 VimScript）；3 使它习惯化。三点反复循环，重点是根据自己的需求迭代，而不是照抄教程装一堆插件——插件是别人为通用需求提炼的，和你的具体需求总有差别。
  - 问题1 边开发边参考网上方案：反复 ALT_TAB 切 Chrome/GVim 很低效，于是用 VimScript + 内嵌 Python 拿到 GVim 顶层 HWND，一键在透明/不透明间切换。
  - 问题2 浏览文档时的窗口滚动：左右分屏参考时，要滚左边就得切焦点再切回来。写 ~Tools_PreviousCursor~ 函数（用 ~wincmd p~ 暂切到前一窗口做 ~<c-y>/<c-e>/gg/G~ 等滚动再切回），绑到 ALT_U/ALT_D，不退出插入模式就能滚动参考文档；同理给 Quickfix 窗口写了滚屏函数。
  - 问题3 Tag Preview 低效：原生 ~CTRL-]~ 会切走当前文档，~<C-W><C-]>~ 又会打印一大串定义让人选且默认上下分屏。自己重撸：ALT+; 在右侧弹出预览窗口并高亮符号，底部显示「共 N 处、当前第几处」，连按 ALT+; 循环切换定义，ALT+SHIFT+; 关闭——全程不切焦点、不切模式，用一周后彻底淘汰原生 tag 功能。
  - 进一步做「函数原型」：忘函数参数时不需要打开整个预览窗口，写函数绑到 ALT_Q，在最底一行循环显示函数原型多处定义；比 YCM 支持语言广（基于 Universal Ctags，覆盖 85 种语言）。
  - 问题4 代码片段：常写的格式化注释框、copyright、带 main 的框架，用 VimScript 一键生成；UltiSnip 虽好但没为 Vim 8/Neovim 做异步优化、打开新文件变慢，所以作者仍用自己的简单实现。
  - 问题5 加速 Cygwin 开发：跨平台要反复用 MinGW/Cygwin 编译测试还得切终端窗口。借 Vim 8/Neovim 的后台任务机制写了 AsyncRun 插件，用 ~:AsyncRun [cmd]~ 替代阻塞式 ~!~，并映射 F7 编译 MinGW（~gcc "%" -o "%<"~）、F8 编译 Cygwin（~d:\cygwin\bin\bash --login -c "gcc % -o %<"~）。
  - 问题6 加速 Android NDK 开发：以前写 NDK 要命令行编译再导进 Eclipse/Android Studio 套 Java GUI，改一处折腾半天。结合 AsyncRun + 少量 Python/VimScript，实现 F9 按 Android 命令行程序编译 NDK 并 adb 上传到 /data/local/tmp 设 755，F10 打开 cmd 经 adb 运行——像开发 PC 命令行程序一样开发 NDK，还支持模拟器和真机。
  - 问题7 高效 Grep：原生 grep 不支持异步，用 AsyncRun 配合：~:AsyncRun! grep -n -R <cword> .~ 或加 ~-cwd=<root>~，一键在当前目录 grep 光标下的符号，结果实时输出到 Quickfix，双击即可跳转。
  - 问题8 日常小工具：如把挤在一起的 HTML 片段一键格式化（~asclib#html_prettify~ 用替换 + ~ggVG=~），还有 GTAGS 支持、一键 touch wsgi 主文件、头文件/源文件快速切换、快速打开 Zeal 查文档等——都是围绕自己习惯写的，通用插件解决不了。
  - 结论与对比：其他编辑器/IDE 的效率是常数，上手后很难再提升；Vim 的效率是变量，越调教越顺手。效率低的三种反面：学会基本用法后不再学新技巧；想学一切技巧反而浪费时间；只摆弄插件，插件做不到的就束手无策。
  - 推荐资料：《Five Minute Vimscript》、~:h index~、~:h quickref~、《Practical Vim》、《Learn Vimscript the Hard Way》、《Vim 中正确使用 Alt 映射》。

  - 一句话概括：一套以数据（销量、投诉销量比、口碑评分）为核心的 15 万以内选车方法——先按动力类型锁定车型范围，再用颜值、使用成本、售后、保值率、舒适度、智能化等指标横向打分，最后给出各类别推荐榜。
  【方法/论点要点】
  - 总方法：不懂车就看直观数据，数据比主观评价更可观。年轻人预算多在 15 万以内（土豪与富二代除外）。
  - 预算换算：15 万落地，燃油车裸车价锁定在 13.6 万以内；纯电/插混（纯电续航 120KM 以上）裸车约 14 万以内（免购置税）；不着自动挡的车型直接 PASS。
  - 选车第一看销量：15 万落地车型月均低于 5000 台要慎重，销量低的车可能随时停产、后期维修保养是问题。
  - 第二看质量：用「投诉销量比」评质量可靠性；2023 年三季度 SUV 投诉销量比均值万分之 63.2、轿车万分之 69.7，高于平均线的一概不考虑（年销 6 万以上的燃油车仅别克君越未过关）。作者把数据都列出，读者可自设质量标准线。
  - 三类车型的入围与投诉（示例）：燃油车 38 款（轩逸、朗逸、速腾、卡罗拉、雅阁、思域等，附各车近一年主要投诉内容）；纯电 9 款（海豚、AION S、秦 PLUS EV、欧拉好猫、ID.3、元 PLUS 等，门槛设为月销 3000 台、投诉比万分之 67.3）；插混/增程 6-7 款（秦 PLUS DM-i、驱逐舰 05、深蓝 SL03/S7、宋 PLUS/Pro DM-i、银河 L7）；作者解释不推荐畅销的宋 PLUS DM-i 是因为「问题太多，大数据说话」。
  - 评价维度按动力类型不同：燃油车看内外颜值、使用成本、售后服务、保值率、舒适度（轿车）/空间（SUV）；增程/插混看颜值、售后、亏电与综合油耗、智能化；纯电看颜值、续航、快充、售后、智能化。
  - 数据来源与结论举例（燃油轿车）：颜值 TOP3 领克 03、长安 UNI-V、吉利星瑞；使用成本最低雷凌、卡罗拉、轩逸；售后满意度最高雷凌、领克 03、轩逸/天籁；5 年保值率最高雅阁、思域、卡罗拉；舒适度最高雅阁、天籁、型格。各指标换算百分制后综合排序。

  - 最终推荐榜：燃油轿车 TOP5（雅阁、思域、领克 03、天籁、长安 UNI-V）、燃油 SUV TOP5（皓影、RAV4 荣放、威兰达、星越 L、博越 L）、纯电 TOP3（秦 PLUS EV、元 PLUS、欧拉好猫）、增程/插混 TOP3（深蓝 S7、深蓝 SL03、驱逐舰 05），每款都列出优点与缺点（如雅阁隔音差/车机差，思域隔音差，领克 03 保养贵等）。
  - 实操建议：买车货比三家，同一城市不同 4S 店落地价也会不同。作者提醒数据会定期更新，当下最优不代表一直最优。

  - 命令提示 vs 补全：「命令提示和补全是两个完全不同的系统，很多时候提示比补全更有用」。输入完 tar 后，灰色即提示参数，并随每个字母动态修正（输入 `-c` 就立刻从解压提示切到压缩提示）；提示基于你的历史命令数据库，用得越多越准；按 `CTRL+F` 采纳整条建议。
  - 智能补全：内容较多时连按两次 TAB 进入「选择模式」，可用光标键或 emacs 键位 `ctrl+f/b/p/n`（前后上下）移动，也可自定义为 `ALT+hjkl`；回车确认，`CTRL+G` 退出。另有路径缩写补全（省去长路径逐层输入）与二级参数补全（如 `svn commit --` 后两次 TAB 选参数）。
  - 快速跳转：`cd -` 后按 TAB 列出本次登录去过的最近路径，输入序号回车即跳（例：`cd -5` 跳到 ~/software/libclang-python3），也可再按 TAB 进选择模式挑选。

    bindkey '\e[1;3A' beginning-of-line   # ALT+上：跳到行首

  - 痛点：作者自称把练习网站（自学SQL网、sqlzoo、牛客网 SQL 面试题）从头到尾刷了一遍，「感觉自身的 SQL 水平飞速上升」，但工作中遇到「复杂 SQL」立刻败下阵来——简单 SQL 会写，一到工作实际就废。
  - 示例（作者当年被难住的那条）：
    #+begin_src sql
    SELECT sum(Domestic_sales+International_sales) as sum_sale, director,
           count(*) as count,
           sum(Domestic_sales+International_sales)/count(*) as avg_sale
    FROM movies left join boxoffice on movies.id = boxoffice.movie_id
    group by director
    having count > 1
    order by avg_sale
    desc limit 1
    #+end_src
  - 核心心法：不管多复杂的 SQL，先归结到最简单的 SQL 法则——凡是 SQL 都分为 select、from、where 三段，复杂 SQL 只是这三段各自不简单，那就**分段解决**。
  - 第 1 步·只解决 from：不关心 select 和 where，先把联表写出来，并想象联表之后生成了一张新表 t1。
    #+begin_src sql
    SELECT *
    FROM movies left join boxoffice on movies.id = boxoffice.movie_id
    where 1
    #+end_src
  - 第 2 步·在 t1 上只解决 select：把 group 等结果集操作放到一边，只盯着要统计的列，逐个函数拆开看（sum、count、sum/count）。
    #+begin_src sql
    SELECT sum(Domestic_sales+International_sales) as sum_sale, director,
           count(*) as count,
           sum(Domestic_sales+International_sales)/count(*) as avg_sale
    FROM t1
    #+end_src
  - 第 3 步·最后再处理结果集：把 select 里的算法放在一边，加上分组、过滤与排序。
    #+begin_src sql
    SELECT ...
    FROM t1
    group by director
    having count > 1
    order by avg_sale
    desc limit 1
    #+end_src
  - 结论：「一个复杂 SQL 其实都是由简单的部分组成，只要你按照这个方法一层层的拆解，你会发现复杂 SQL 不过如此。」（作者标注原文未完待续）
